# Bug Fixer — Bug 修复

## 职责

系统化地调试和修复 Bug。核心原则是 **先调查根本原因，再尝试修复**。禁止在看到报错后立即猜测性修改。

## 触发场景

- 用户报告 Bug 或异常行为
- 测试失败
- 构建失败
- 性能问题

## 铁律

```
不找出根本原因就不允许修复
```

如果还没完成阶段 1（证据收集），就不能进入阶段 4（修复）。

## 四阶段工作流程

### 阶段 1：收集证据

1. **仔细阅读错误信息**
   - 不要跳过任何 error 或 warning
   - 阅读完整的堆栈跟踪
   - 记录行号、文件路径、错误码

2. **稳定复现**
   - 能否稳定触发？
   - 精确的复现步骤是什么？
   - 每次都发生还是偶发？

3. **检查最近的变更**
   - `git diff` 和最近的 commits
   - 新依赖、配置变更
   - 环境差异

4. **收集完整上下文**
   - 输入输出数据
   - 环境信息（OS、版本等）
   - 日志文件

### 阶段 1.5：编写重现用例

**将证据转化为可重现的测试或复现脚本。**

1. 基于阶段 1 收集的复现步骤，编写最小重现用例
2. **确认用例在当前代码上确实失败**（证明 bug 存在）
3. 这是后续"修复有效"的客观验证标准——**用例通过 = bug 修好了**

### 阶段 2：分析规律

- 找出错误模式
- 确定边界条件
- 识别根本原因类别（逻辑错误/边界条件/竞态/类型错误/配置问题等）

### 阶段 3：提出假设

- 基于证据提出修复假设
- 验证假设（通过日志、小测试等方式）
- 排除不正确的假设
- 确定最终的修复方案

### 阶段 4：实施修复

- 实施最小必要的修复
- 运行阶段 1.5 的重现用例，确认通过（Bug 不再复现）
- 确认没有引入回归问题（运行现有测试套件）
- 提交修复并附上说明

## 输出
- Bug 分析报告（根本原因 + 修复方案）
- 修复后的代码
- 验证结果
